# native-launch

## ADDED Requirements

### Requirement: FreeRDP version floor is enforced at runtime

The application SHALL detect the `xfreerdp` binary and its version before offering the native connect method, and
SHALL disable the native method — never attempt a launch — when FreeRDP is absent or below 3.30.0, stating the
detected version and the required floor in the disabled reason (NFR-8, §9). An unparseable version SHALL be treated
as below the floor.

#### Scenario: FreeRDP below the floor

- **WHEN** the detected `xfreerdp` version is lower than 3.30.0
- **THEN** the native method is shown disabled with the detected version and the 3.30.0 floor stated, no subprocess
  is spawned, and the web method remains available

#### Scenario: FreeRDP absent

- **WHEN** no `xfreerdp` binary can be found at the packaged or configured path
- **THEN** the native method is shown disabled stating FreeRDP was not found, and no launch is attempted

#### Scenario: Version at or above the floor

- **WHEN** the detected version is 3.30.0 or newer
- **THEN** the native method is offered subject to the resource's connectable state (§7.4)

### Requirement: Native sessions launch FreeRDP as a subprocess with the upstream AVD invocation

The native launcher SHALL launch `xfreerdp` as a subprocess (D-1) with the composed configuration file and the
upstream AVD options `/gateway:type:arm /sec:aad` (§2.2, §5.1.1), and SHALL NOT link `libfreerdp`. A native launch
on a connectable Cloud PC from a cold start SHALL produce a visible session window with no manual file handling
within the NFR-3 budget, TCP-only (FR-2-AC-4).

#### Scenario: Cold-start native connect

- **WHEN** the user invokes Connect (Native) on a running Cloud PC from a cold application start
- **THEN** a FreeRDP session window appears within 12 s (p95), of which config acquisition took ≤ 3 s, with no
  manual file handling at any step

#### Scenario: Subprocess crash does not take down the client

- **WHEN** a FreeRDP session subprocess crashes
- **THEN** the application continues running, reports the session end per the §9 taxonomy, and other live sessions
  are unaffected

### Requirement: Configuration handoff is file-based with enforced hygiene

The launcher SHALL write the composed configuration to a file with `0600` permissions in a user-private directory,
at a path generated by the application (§10.4), SHALL delete the file once the subprocess has started, and SHALL
delete it on every failure path. Configurations SHALL never be persisted beyond the handoff (§5.2, §10.1).

#### Scenario: Handoff file lifecycle on success

- **WHEN** a native launch succeeds
- **THEN** the config file was created `0600` in a user-private directory and no longer exists once the subprocess
  has started

#### Scenario: Handoff file lifecycle on spawn failure

- **WHEN** the subprocess fails to spawn after the config file was written
- **THEN** the file is deleted before the failure is reported

### Requirement: Feed-sourced data never reaches the command line

The launcher SHALL execute FreeRDP with an argument vector (never via a shell) built from a fixed, application-
controlled option set; feed-sourced values SHALL appear only inside the configuration file, and no feed-sourced
string SHALL introduce, extend, or alter a command-line option (§10.4).

#### Scenario: Injection-shaped feed value

- **WHEN** a configuration is composed from a feed response containing option-injection-shaped values (§13.3)
- **THEN** the argument vector contains only the fixed options and the app-generated file path, and the hostile
  value is present, if at all, only inside the config file

### Requirement: Exit status maps onto the error taxonomy with web fallback in one action

The launcher SHALL track each child process and map its exit status and captured stderr onto the §9 error taxonomy;
any native launch failure SHALL present the web-launch fallback in the same failure surface, actionable in one step
(FR-2-AC-5). Unrecognized exit outcomes SHALL map to a generic session failure with logs captured under §10.7
redaction, never silently ignored.

#### Scenario: Gateway rejects the connection

- **WHEN** FreeRDP exits reporting a gateway rejection
- **THEN** the user sees a toast naming the reason with retry (fresh silent token) and web-launch fallback offered
  in that same surface

#### Scenario: Unknown exit code

- **WHEN** FreeRDP exits with a code the mapping table does not recognize
- **THEN** the failure is reported as a session failure, the exit code and redacted stderr are logged for triage,
  and web fallback is offered

### Requirement: Stopped or deallocated Cloud PCs produce a starting state, not an error

A native connect to a stopped or deallocated Cloud PC SHALL be treated as a normal first-run case: the UI shows a
starting state with progress while FreeRDP's own orchestration retry runs, bounded by the §7.4 timeout; no failure
is surfaced until the timeout elapses (§7.4, §9).

#### Scenario: Connect to a deallocated Cloud PC

- **WHEN** the user connects natively to a deallocated Cloud PC
- **THEN** a starting state with progress is shown, the launcher waits on FreeRDP's orchestration retry, and a
  failure appears only after the stated timeout

### Requirement: Session drops reconnect only through re-acquisition and re-validation

On a session drop, the launcher SHALL invalidate the in-memory configuration for that (account, resource) and the
reconnect path SHALL re-acquire and re-validate the configuration before any new subprocess is launched (§5.2, §9).

#### Scenario: Mid-session drop and reconnect

- **WHEN** a live native session drops and the user accepts the reconnect prompt
- **THEN** the configuration is re-fetched from the provider and re-validated per §10.1 before the new launch, and
  the previous configuration is not reused

### Requirement: Proxy configuration is propagated to the session subprocess

The launcher SHALL explicitly pass the effective proxy configuration to the FreeRDP subprocess, because the child
does not inherit the client's HTTP proxy settings (§5.9); a session-path proxy failure SHALL be reported
distinguishably from offline and from auth/control-plane proxy failures.

#### Scenario: Auth succeeds but the session path is proxied

- **WHEN** sign-in and Graph calls succeed through a proxy and a native session is launched in the same environment
- **THEN** the subprocess receives the proxy configuration, and if the session path is blocked the error names the
  session-path proxy specifically rather than reporting offline

### Requirement: Redirection defaults follow the Phase 1 matrix

Native sessions SHALL default to: clipboard text on, audio out on, drive redirection off, microphone off; drive
redirection SHALL be offered only as an explicit per-resource folder choice; printers, smartcard, and camera are
deferred and USB is out of scope (§5.5). Redirection SHALL be presented as negotiated: a channel the host refuses
is an informational condition, not a client error. Flag spellings SHALL be verified against `xfreerdp --help` at
FreeRDP 3.30 before being relied on.

#### Scenario: Default session channels

- **WHEN** a native session is launched with no per-resource overrides
- **THEN** clipboard text and audio out are requested, and no drive, microphone, printer, smartcard, camera, or USB
  redirection is requested

#### Scenario: Host refuses a requested channel

- **WHEN** the host's RDP properties disable a channel the client requested
- **THEN** the client reports the channel as unavailable-by-host-policy informationally and the session continues

### Requirement: Phase 1 display scope

Native sessions SHALL support a single monitor, windowed and fullscreen, with dynamic resolution on window resize
where the client supports it and integer scaling only (§5.6). On Wayland the session runs through XWayland — the
§5.6 limitations are the permanent Phase 1 position and SHALL appear in user-facing documentation.

#### Scenario: Window resize

- **WHEN** the user resizes the session window on a client supporting dynamic resolution
- **THEN** the remote resolution follows the window size

### Requirement: Concurrent sessions

The application SHALL support at least 2 concurrent native sessions and SHALL soft-warn when the user opens more
than 4 (NFR-5). Sessions SHALL NOT share handoff files or per-child state.

#### Scenario: Second concurrent session

- **WHEN** a second native session is launched while one is live
- **THEN** both sessions run independently and closing either leaves the other connected

#### Scenario: Fifth concurrent session

- **WHEN** the user launches a fifth concurrent native session
- **THEN** a soft warning is shown and the launch proceeds if confirmed
